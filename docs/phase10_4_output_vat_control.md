# 10.4 — Податкові зобов’язання та звірка з Головною книгою

Дата: 16.09.2026. Базовий commit: `5e640ec1300f6da3ecb3917c1b914cc5b9ef6019`.

## Реалізовано

Критерій S06 із аудиту 10.1: OUTPUT recognition і його проводки звіряються,
закритий період не змінюється мовчки. **10.4 backend V1 завершено в межах
автоматичного OUTPUT-визнання внутрішніх торговельних операцій у UAH.**

Додано контроль кожної події ПДВ проти пов’язаної проводки:

- наявність рівно однієї проводки для ненульового податку;
- відсутність зайвої проводки за нульового ПДВ;
- статус проведення, дата, сума та кореспонденція рахунків;
- зв’язок сторнувальної проводки з проводкою початкової події;
- правильний тип джерела та валюта;
- окремий очікуваний і фактичний підсумок за період.

Навіть якщо дві помилки на +1 і −1 грн дають нульову загальну різницю,
`matched` буде `false`: перевіряється кожне джерело. Відсутня проводка,
неправильний рахунок при збалансованій проводці або дата в іншому місяці
також дають явну розбіжність. Перевірка дати знаходить проблему з обох боків
межі періоду: у місяці події та в місяці помилкового запису.

Сторнована початкова проводка залишається в оборотах разом зі своєю
сторнувальною проводкою; її не вилучають лише через статус `reversed`.
Рахунки визначаються через налаштовані ролі компанії, а не жорстко задані ID.

Посилено OUTPUT posting/reversal: NaN та нескінченні суми відхиляються до
запису. Юридичний доказ INPUT credit не може бути джерелом OUTPUT проводки.

## API

`GET /api/v1/companies/{company_id}/vat-controls/output-gl`

Обов’язкові параметри: `date_from=2026-09-01&date_to=2026-09-30`.
Право доступу: `journal_entries.read` у відповідній компанії.

Повертає:

- `expected_output_vat` — сума подій OUTPUT мінус сторнування, за датою подій;
- `posted_output_vat` — кредит мінус дебет ролі TAX_SETTLEMENT у пов’язаних
  проведених проводках, за датою проводок;
- `difference` — фактичний підсумок мінус очікуваний;
- `matched` — нульова різниця **і** відсутність усіх виявлених проблем;
- `issues` — код проблеми та IDs події, розрахунку, документа і проводки;
- `event_count` — кількість перевірених подій, включно з джерелами з іншою
  датою, якщо їхні проводки потрапили в запитаний період.

Обмеження: до 367 календарних днів та 10 000 подій у запиті. Перевищення
повертає 422 із вимогою зменшити інтервал; усічений успішний звіт не видається.
Неповні або непридатні налаштування ролей рахунків повертають 409.

API лише читає. Воно не проводить документи, не виправляє дані та не відкриває
періоди. Закритий період залишається доступним для звірки. Всі події, проводки
та рядки читаються одним SELECT, щоб результат не змішував різні стани GL.

- Числові перевірки: оплата, поставка, аванс за замовленням і їх сторнування;
  VAT0; незавершена проводка; пропущена проводка; неправильна дата/рахунок;
  взаємне погашення помилок у підсумку; зв’язок сторнування; NaN/Infinity.
- PostgreSQL: справжнє визнання і GL; навмисні пошкодження лише в ізольованих

  чужа компанія; читання закритого періоду; перевірка відсутності записів API.
- Звірку додано до PostgreSQL-сценаріїв 10.3: часткова оплата/поставка в обох

  змішані ставки, кілька платежів, перенесення й скасування перенесення.
- API: 401 без автентифікації, 403 без прав компанії, правильна передача

## Межі та наступний крок

Це звірка **автоматичного OUTPUT recognition з його GL-джерелами**. Вона
не є повним сальдо рахунку 641: INPUT, ручні записи, сплата податку, окремі
події повернень та юридичні РК мають інші джерела. Їх консолідація належить
10.7/10.8. Події 643/702, що обліковують перекласифікацію авансу при поставці,
не створюють нового OUTPUT зобов’язання і не додаються до цього підсумку.

Звірка виявляє порушення між наявними подіями та проводками; вона не доводить,
що всі реальні господарські операції були введені в ERP, і не перераховує
нормативну правильність кожної першої події. Налаштування рахунків беруться
з чинного профілю компанії; історичні зміни профілю потребують окремої
міграції. Раніше зафіксовані межі авансів V1 з 10.3 залишаються чинними.

Загальна нормативна основа дати зобов’язань — п. 187.1:
[ДПС, розділ V ПКУ](https://tax.gov.ua/nk/rozdil-v--podatok-na-dodanu-vartist/).
Нові спеціальні режими чи правила декларації цим checkpoint не додаються.
