# 10.5 — Податковий кредит: підтвердні дані, період і проводки

Дата: 16.09.2026. Базовий commit: `e6ba202abb424de7361b3e89775f60066b4fc449`.

## Що реалізовано

Новий серверний процес для звичайних внутрішніх придбань у UAH за методом
першої події: **підтверджена користувачем реєстрація ПН → допустимий період →
наявна економічна підстава → незмінюваний доказ → подія кредиту → проводка**.

- Дату доступності кредиту обчислює сервіс. API не приймає довільне
  `credit_available_date` від користувача.
- Для статусів pending/suspended/rejected створення кредиту блокується.
  Для registered потрібні дата реєстрації з ЄРПН та посилання/ідентифікатор
  квитанції. **Це атестація уповноваженого користувача, а не онлайн-перевірка
  справжності квитанції чи статусу ЄРПН.**
- ІПН покупця/постачальника звіряються з датованими налаштуваннями на дату
  ПН. Статус покупця також перевіряється на обчислену дату кредиту. Рахунок
  має містити перевірені VAT snapshots; legacy-налаштування не підміняються.
- Сума кредиту має відповідати ставці розрахунку і не перевищувати ще не
  використану економічну підставу обраного періоду. Однієї ПН без оплати або
  надходження недостатньо. Порівнюються і база, і податок.
- Дані атестації, результат розрахунку та версія правила зберігаються окремо
  від бухгалтерських сум. Прив’язка до доказу має складений FK із company
  та calculation IDs.
- Повтор із тим самим `request_key` і payload повертає наявну заявку;
  інший payload із тим самим ключем відхиляється. Запис доказу, подій,
  проводок і заявки виконується однією транзакцією.
- Сторнування створює новий доказ і податкові/бухгалтерські записи; початкові
  суми не переписуються. Повторне сторнування на ту саму дату не дублюється.
- Закритий період відхиляє всю операцію. Рахунок із чинною заявкою кредиту
  не можна скасувати до сторнування заявки. Зворотне датування через уже
  наявну пізнішу історію вимагає окремого контрольованого коригування.

## Версія правила та її межі

`ua-domestic-pn-first-event-2026-09-17` застосовується до звичайних ПН від
01.08.2023. Дата перевірки правила (`POLICY_VERIFIED_THROUGH`) — метадані,
а не щоденна заборона нових документів. Межа чинності задається окремо через
`POLICY_UNTIL`, коли визначена дата завершення відповідного режиму.
Майбутні документи, реєстрації та періоди залишаються забороненими.

### Доповнення 17.09.2026: кредит за авансом

Кредит доступний до рахунку за підтвердженим авансом, прив’язаним до
закупівельного замовлення. Потрібні ті самі підтвердження ПН та перевірки
сум/ставок. Скасування авансу з чинним кредитом блокується.
Перенесення на відповідний рахунок сторнує доказ замовлення і створює
доказ рахунку в одній транзакції: загальний кредит не збільшується.
Повторний запит не дублює кредит. Нову заявку можна сторнувати стандартним
процесом. Зворотне скасування самого перенесення з історією доказів не
підтримується автоматично: чинний захист від переписування історії збережено.

Для підтримуваного періоду п. 89 підрозділу 2 розділу XX передбачає строки
реєстрації 5-го/18-го числа наступного місяця залежно від половини місяця
складання ПН. Джерело: [ДПС про строки реєстрації](https://sumy.tax.gov.ua/media-ark/news-ark/782430.html).

Своєчасно зареєстрована ПН допускає місяць складання; запізніла — не раніше
місяця реєстрації. Перевіряється 365-денний строк і його переривання на
підтверджені періоди зупинення. Обраний місяць може бути не пізнішим за
місяць, у якому закінчується строк. Дата подання декларації сюди не входить.
Джерела: [ДПС про формування кредиту після зупинення](https://tax.gov.ua/nove-pro-podatki--novini-/854626.html),
[ДПС про запізнілу реєстрацію](https://ck.tax.gov.ua/diialnist/podatkoviy-audit/povidomlennya/1013736.html).

Інтервали зупинення задаються як `[suspended_on, resumed_on)`: день
відновлення не додається вдруге. Потрібне посилання на рішення. Перекриття,
зупинення до дати ПН, завершення після реєстрації та спроба відновити вже
вичерпаний строк відхиляються. Це дані атестації; автентичність рішення
сервіс сам не підтверджує.

Окрема підтримка потрібна для ПН до 01.08.2023 з перехідними правилами,
касового методу, митних/спеціальних документів, юридичних РК, судових випадків
із неоднозначною датою реєстрації. Вони не переводяться автоматично на це
правило. Наявність нижчорівневого enum доказу не означає готового процесу.

## API та приклад

Префікс: `/api/v1/companies/{company_id}/input-vat-credit`.

| Метод і маршрут | Дія | Право |
|---|---|---|
| POST `/assess` | Попередня перевірка строків за введеними даними; не перевіряє БД/економічну підставу й не створює кредит | `journal_entries.read` |
| POST `/claims` | Повна перевірка та атомарне визнання | `journal_entries.approve` |
| GET `/claims?after_id=0&limit=100` | Історія заявок своєї компанії | `journal_entries.read` |
| POST `/claims/{id}/reverse` | Сторнування з `reversal_date` | `journal_entries.approve` |

Приклад тіла POST `/claims` (умовні реквізити):

```json
{
  "request_key": "supplier-pn-123-line-1",
  "tax_calculation_id": 42,
  "invoice_number": "123",
  "invoice_date": "2026-08-10",
  "registration_status": "registered",
  "registered_on": "2026-09-06",
  "receipt_reference": "archive/receipt-123",
  "buyer_vat_number": "111111111111",
  "supplier_vat_number": "222222222222",
  "claim_period": "2026-09-01",
  "taxable_base": "60.00",
  "tax_amount": "12.00",
  "suspensions": []
}
```

Реєстрація 06.09 є запізнілою для ПН 10.08: серпень відхиляється, вересень
допускається за виконання інших перевірок. Проводка отримує дату не раніше
06.09. Своєчасна реєстрація може дозволити попередній місяць, але запис у
закритий період все одно відхиляється.

Помилки даних/періоду/повторного ключа повертають 409, структурно неправильні
запити — 422. Відсутність доступу — 401/403. Виконавець береться із сеансу.

## Що залишається відкритим

**10.5 backend V1 охоплює описаний звичайний invoice-based процес.** Юридичний
кредит на аванс до комерційного рахунку та перенесення такого доказу між
замовленням/рахунком ще не реалізовані. Економічний аванс із 10.3 не
перетворюється автоматично на кредит.

Для цієї версії обсяг заявленого кредиту має вже повністю покриватися
економічними подіями. Один активний номер ПН у межах одного розрахунку не
розбивається на кілька нових доказів у різні періоди. Повна модель ПН із
розподілом рядків/сум, квитанціями та РК належить 10.6/10.7; перевірка
транспорту/КЕП — блоку 21. Нижчорівневі внутрішні сервіси попередніх етапів
залишаються сумісними, але новий публічний API не обходить перевірку політики.

Прогалина P10-05 закрита в частині контролю введених даних і періодів цього
V1-процесу. Автоматичну перевірку ЄРПН, всі винятки законодавства та повну
юридичну модель ПН цей checkpoint не оголошує завершеними.
