# Повний перерахунок лікарняного після нарахування зарплати

Статус: ФІНАНСОВИЙ ШЛЯХ РЕАЛІЗОВАНО ТА ПЕРЕВІРЕНО. Завершення: 27.10.2026.
Окремий ризик прав власника PostgreSQL наведено нижче; весь блок 13 не закривається.

## Погоджене завдання

Не змінювати старі джерела, не скасовувати фактичні виплати для вигляду.
Виправлення створює перевірену нову версію лікарняного й зарплатного розрахунку,
податкові різниці та узгоджені бухгалтерські записи. Повтор запиту не дублює
нарахування, виплату або повернення.

Переплата не утримується автоматично з наступної зарплати. Користувач
підтвердив: тільки документоване повернення або окреме законне утримання.

## Обов'язкове приймання всього пункту

- Перевірені джерела виправлення; незалежне погодження, компанійні права,
  правильний працівник/страховий випадок, незмінна первісна історія.
- Новий розрахунок із чинними для відповідного місяця правилами; урахування
  переходу між місяцями, продовження випадку й пов'язаних договорів працівника.
- Включення нової версії в зарплату й повторний розрахунок ПДФО/ВЗ/ЄСВ;
  узгоджені розрахунковий листок, податкові й працівницькі залишки.
- Фінансова різниця після непроведеного, проведеного, частково й повністю
  виплаченого розрахунку; реальні банківські/касові платежі зберігаються.
- Доплата без повторної виплати старої суми; переплата окремо, її часткове
  повернення/погоджене утримання, захист від подвійного зарахування платежу.
- Окремі різниці роботодавця та ПФУ, уже отримане фінансування, необхідність
  повернення надлишку фонду й зв'язок із підтвердженим платіжним документом.
- Відкритий період бухгалтерського коригування, історичні залишки, звірка
  податків і проводок; заборона непідтверджених або неповних результатів.
- API всього процесу; повтори, конфлікти й конкурентність; повний відкат
  невдалої транзакції; міграції й захист історії в PostgreSQL.
- Позитивні наскрізні тести, залежна регресія, актуальна документація,
  погоджений commit/push. Проміжні успіхи не закривають цей пункт.

КЕП/подання регламентованих документів не входять у цей пакет (блок 21).
Формування всіх Д1/4ДФ/Д5/Д6 залишається окремим пунктом 13.14, але джерела
та різниці цього коригування мають зберігатися для їх подальшого використання.

## Нормативна опора

ПФУ: виправлення отриманого фінансування на зменшення та підтвердження повернення:
https://www.pfu.gov.ua/2170964-yak-podaty-koreguyuchu-zayavku-rozrahunok-na-zmenshennya-sumy-likarnyanyh/

## Реалізований шлях

1. Створити та незалежно перевірити виправлені страхові відомості для того самого
   працівника й страхового випадку. Реєстрація запиту зберігає `pending_review`.
2. `POST /api/v1/companies/{company_id}/payroll-sick-corrections/apply` приймає
   `original_sick_id`, `insurance_evidence_id`, `correction_date`, `request_key`,
   `reason`. Потрібні права `employees.manage` і `journal_entries.create`.
3. Одна транзакція створює нові версії всіх пов'язаних листків і зарплатних
   розрахунків працівника за зачеплені місяці, обчислює податки, проводить різницю
   та змінює відповідний запит на `applied`. Невдача відкочує весь пакет.
4. Звичайний сервіс виплати працює з новим ідентифікатором зарплатного розрахунку.
   Він враховує платежі попередніх версій, аванси й підтверджені повернення.
5. Повернення підтверджується вже проведеним банківським документом через
   `POST /api/v1/companies/{company_id}/payroll-sick-corrections/returns`:
   `calculation_id`, `journal_entry_id`, `bank_account_id`, `kind` (`employee`
   або `insurer`), `request_key`, `document_reference`. Цей endpoint не створює
   платіж і не утримує кошти із зарплати. Документ має повністю відповідати
   сумі та напрямку повернення; один документ не зараховується повторно.
6. `GET /api/v1/companies/{company_id}/payroll-sick-corrections/{application_id}`
   повертає застосований пакет і розрахунки на `as_of` (типово поточна дата).
   Наступні застосовані виправлення враховуються за датою, первісні посилання
   пакета залишаються в історії.

## Межі безпечного використання

- Старі джерела, проводки й фактичні виплати залишаються незмінними. Старий
  destructive-replacement guard залишається ввімкненим; застосування виконується
  через новий атомарний процес версій.
- Для повторного обчислення потрібна збережена початкова база розрахунку з
  PostgreSQL-печаткою. Відсутню історію система не відновлює припущеннями.
- Коригування проводиться у відкритому бухгалтерському періоді, не раніше
  завершення зачеплених зарплатних місяців. Закритий попередній період не
  переписується.
- Міграції 061–063 залежать від попередніх міграцій 043–060. Перевірка оновлення
  виконується на окремій копії PostgreSQL; успіх копії не означає автоматичного
  оновлення робочої бази.
- Для запиту, джерела якого ще не використані зарплатою, збережено окремий
  `apply_unlinked_sick_correction` із незалежним погодженням. Він не може
  застосовуватися до вже використаних джерел.

## Окремий наявний ризик конфігурації PostgreSQL

Перевірка `tests/test_cash_gl_role_bypass_postgresql.py` виявляє раніше
задокументовану проблему: поточний користувач БД володіє таблицями та може
вимикати користувацькі тригери. Це не вважається успішною перевіркою.
Розділення ролей описане в `docs/phase13_db_role_separation_plan.md` і не
реалізоване цим фінансовим пакетом. Звичайні операції API та зміни SQL із
увімкненими тригерами перевіряються; захист від адміністратора-власника БД
не заявляється. Цей пункт не означає загального закриття всього блоку 13.
