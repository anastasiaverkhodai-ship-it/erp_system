# 12.11 — звіти ОЗ; 12.12 — завершальна перевірка

## Обсяг

Завершення backend/API блоку 12: звіт про рух і залишки основних засобів,
відомість амортизації, незалежна звірка з бухгалтерськими проводками та
наскрізні перевірки життєвого циклу. Це не команда закриття фінансового року
і не підтвердження достовірності всіх наявних у базі тестових документів.

## API

Усі маршрути потребують `journal_entries.read` у відповідній компанії:

- `GET /api/v1/companies/{company_id}/fixed-asset-reports/movement`
- `GET /api/v1/companies/{company_id}/fixed-asset-reports/depreciation`
- `GET /api/v1/companies/{company_id}/fixed-asset-reports/gl-reconciliation`

Обов'язкові параметри `date_from`, `date_to` включають обидві межі періоду.
Перші два маршрути також приймають `fixed_asset_id`. Чужа картка недоступна;
невірний період повертає 422, відсутність права — 403. Звірка рахунків завжди
охоплює всю компанію: спільний рахунок не можна коректно звірити з однією карткою.
Суми передаються десятковими рядками без перетворення у float.

### Рух і залишки

Для кожного ОЗ і разом: первісна/переоцінена вартість, накопичений знос та
залишкова вартість на початок і кінець; збільшення та зменшення вартості й
зносу за період. Події деталізовані до виду, дати, ідентифікатора операції,
сторнованого оригіналу й пов'язаних проводок. Повний продаж залишає нульовий
баланс у звіті, хоча картка зберігає історичну вартість.

`current_name` та `current_status` — поточні реквізити картки, не її історичний
стан. Фінансові суми відновлюються за подіями. Чернетка з вручну заповненою
вартістю сама по собі не створює бухгалтерського залишку.

### Амортизація

Суми нарахування, сторнування і чистий підсумок, період нарахування, дата
проводки, метод та фактичний виробіток. Для виробничого методу нульовий виробіток
показується як подія без обов'язкової нульової проводки. Фільтр дат застосовується
до дати відображення у бухгалтерії, а `period_start/end` пояснюють місяць нарахування.

### Звірка

Очікувані суми беруться з подій ОЗ та деталізації початкових залишків.
Окремо читаються проведені/сторновані журнали. Для кожного рахунку порівнюються
початковий баланс, дебетовий оборот, кредитовий оборот і кінцевий баланс.
Знак балансу: дебет мінус кредит; різниця: бухгалтерія мінус очікуваний субоблік.

Контролюються рахунки вартості й зносу з карток, а також рахунки з префіксами
10/11/12/13, навіть без картки. Кореспонденція конкретної операції перевіряється
повністю, включно з витратами, капітальними інвестиціями та рахунком переоцінки.
Інші операції на рахунках витрат не включаються у баланс ОЗ.

`issues` містить конкретні пояснення: відсутня/непроведена/зайва проводка,
невірна дата, рахунок або сума, ручний запис без події ОЗ, розбіжність початкових
залишків, відсутня основа введення в експлуатацію, від'ємний відновлений залишок.
Позитивний `matched` / `reconciled` можливий лише без таких зауважень.
Фільтр однієї картки зберігає загальні зауваження звірки компанії.

## Історичність і джерела

- Сторнований оригінал залишається у звіті до дати власне сторнування.
  Пізніше сторнування не змінює раніше сформований період.
- Введення, поліпшення, переоцінка/зменшення корисності, амортизація,
  часткове/повне вибуття та їх сторнування мають окремі знаки руху.
- Звичайний ремонт показується як витрата без збільшення вартості ОЗ.
- Продаж використовує вже проведений документ: `sale_net_amount` інформаційна,
  звіт не повторює дохід, борг покупця чи ПДВ.
- Нові введення зберігають `cost_snapshot`: точні ідентифікатори розподілів,
  рахунки джерел і суми; сторнування зберігає ту саму основу.
- Для старих введень без snapshot використовується незалежна історія розподілу
  придбання на момент створення введення. Неоднозначна історія (зокрема
  сторнування розподілу з тим самим часом транзакції) повертає зауваження для
  перевірки джерел. Суми не копіюються з журналу, який потрібно звірити.
- HTTP-звіти працюють у `REPEATABLE READ, READ ONLY`: усі запити бачать один
  знімок PostgreSQL, одночасне проведення іншою сесією не змінює половину звіту.

## Міграція

`8fa12512c001` після `8fa12510c004` додає nullable JSON `cost_snapshot`.
Існуючі фінансові суми, картки та проводки не змінюються; штучного заповнення
історії з бухгалтерських проводок немає. Downgrade відмовляє, якщо вже є збережені
snapshots, щоб не втратити джерела історичних сум.

## 12.12 — сценарії перевірки

- придбання → введення → сторнування → звіт на попередню й поточну дату;
- початкові залишки зі зносом → амортизація → часткове вибуття → звірка з ОСВ;
- сторнування вибуття → амортизації → початкових залишків, нульовий результат;
- поліпшення → переоцінка → послідовне сторнування, незалежні суми;
- повний продаж з проведеного джерела → нульовий баланс → сторнування вибуття;
- нульовий виробіток без зайвої проводки;
- навмисно змінені суми/дати/статус проводок та компенсуючі ручні записи;
- межі компаній, права API, неправильні дати, відсутність записів від GET;
- міграція upgrade/downgrade, збереження даних, заборона втрати snapshot;
- паралельна зміна журналу не змінює вже відкритий знімок звіту;
- повна регресія всього проєкту в окремій копії PostgreSQL.

Команда повної перевірки:

```bash
PYTHONPATH=. .venv/bin/python scripts/run_postgresql_regression_copy.py tests
```

Міграція застосована до `8fa12512c001`; `alembic check` не виявив розбіжностей.
Offline SQL успішно згенеровано. Порівняння кількості записів і контрольних сум

Звірку прочитано для 111 компаній на 30.09.2026. У 54 тестових компаніях
знайдено по одній старій картці `in_service` без введення/початкового залишку;
це точні збіги шаблонів `FAD company …` та користувача `fad-…@example.test`
з колишнього тестового seed. Подій введення, початкових залишків ОЗ,
амортизації та вибуття у цій базі немає. У компанії №1 карток ОЗ немає.

Звірка повернула `missing_asset_basis` для кожної з цих 54 карток, без інших
типів розбіжностей. Вона не підтверджує неіснуючі бухгалтерські залишки й не
створює фіктивні проводки. Видалення старих тестових компаній/карток не входить
у реалізацію звітів; вони збережені. Наскрізні фінансові сценарії перевіряються
на коректно створених документах у тимчасових схемах та копії бази.
