# 12.4 — Введення основних засобів в експлуатацію

## Поведінка

Підтверджені активні витрати придбання переносяться з рахунків джерел на рахунок
основного засобу одним збалансованим журналом через штатний механізм проведення.
Після успіху картка має стан `in_service` і дату введення. Нового боргу перед
постачальником або повторного ПДВ ця операція не створює.

Сторнування створює окрему подію та зворотний журнал, повертає картку в
`ready_for_commissioning`, очищає дату введення. Початкові подія та проводка
зберігаються. Повторне введення можливе новим запитом після сторнування;
дата не може передувати останній події цього активу.

## API та права

Префікс: `/api/v1/companies/{company_id}/fixed-assets/{fixed_asset_id}`.

| Маршрут | Призначення | Право в компанії |
|---|---|---|
| `POST /commissionings` | Введення: request_key, commissioning_date | journal_entries.post |
| `GET /commissionings` | Історія введень і сторнувань | journal_entries.read |
| `POST /commissionings/{id}/reverse` | Сторнування: reversal_date | journal_entries.reverse |

Використано наявні бухгалтерські права. Суміжні маршрути карток і витрат також
тепер перевіряють права в компанії: read/create/update/reverse відповідно до дії.
Самої авторизації користувача недостатньо. Невідома компанія або чужий актив
не дозволяють виконати операцію.

## Захист цілісності

- Стан готовності, додатна скінченна вартість, ліквідаційна вартість, строк,
  метод, активні рахунки та довідники перевіряються перед проведенням.
- Сума активних витрат дорівнює вартості картки; витрати не можуть перевищувати
  дебет джерела. Джерело — проведений, не сторнувальний журнал тієї самої компанії.
- Дати джерела, визнання витрат і введення узгоджені; майбутнє введення чи
  сторнування заборонено. Для операції потрібен відкритий період.
- Блокування компанії серіалізує зміни картки, придбання та введення. Ідентичний
  повторний запит повертає ту саму подію; інші реквізити з тим самим ключем
  відхиляються. Повторне сторнування на ту саму дату повертає наявну подію.
- Загальні маршрути журналу не можуть змінити, провести, видалити або сторнувати
  журнал введення поза його життєвим циклом.
- Джерело з активними витратами придбання не можна сторнувати. Спочатку треба
  сторнувати введення, потім розподіл витрат, потім початкову проводку.
- Після введення загальне редагування картки та зміни її витрат заблоковані.
  Зміни експлуатації, поліпшення та інші наступні операції належать окремим
  підпунктам блоку 12. Створити `in_service` через звичайну картку також не можна.
- API володіє транзакцією: помилка відкочує подію, журнал і стан активу разом.
- Складені зовнішні ключі захищають межі компаній; окреме обмеження забороняє
  одночасне джерело введення та будь-яке інше джерело в тому самому журналі.

## Перевірки

Ізольовані PostgreSQL-схеми: власні компанії, рахунки, періоди та активи;
без залежності від випадкових записів у робочій базі. Покриття включає життєвий
цикл, повтори, одночасні запити, права API, чужу компанію, закритий період,
невірні дати/суми/рахунки, обхід через загальний журнал або картку, відкат при
помилці проведення, зовнішні ключі та upgrade/downgrade міграцій.

```bash
PYTHONDONTWRITEBYTECODE=1 RUN_POSTGRES_E2E=1 .venv/bin/python -m pytest -q -p no:cacheprovider
.venv/bin/python -m alembic current
.venv/bin/python -m alembic check
git diff --check
```

Локальна міграція `8e124c09a671` застосована; `alembic check` не виявив
розбіжностей. Перевірка локальних даних: подій введення ОЗ 0, активів у стані
`in_service` без події введення 0. Фінансових записів під час завершення 12.4
не змінювали. Початковий тест, який використовував робочу базу й міг пропускати
перевірку через відсутність чернетки, замінено ізольованими сценаріями.
