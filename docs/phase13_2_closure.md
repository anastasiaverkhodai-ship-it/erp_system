# 13.2 — працівники та кадрові довідники

## Обсяг

Backend/API карток працівників, підрозділів, посад та вже створеної основи
трудових договорів. Є платіжні реквізити, компанійний доступ, журнал змін,
перевірки цілісності та ізольовані PostgreSQL-тести.

Це не закриття всього блоку 13. Накази й кадрові події з датою набрання чинності,
переведення, історія окладів, повна підтримка сумісництва та кадровий процес
звільнення належать 13.3. Табелі, розрахунок зарплати, податки й виплати — наступні
підпункти. Поточний журнал 13.2 зберігає фактичні зміни даних і автора; він не
замінює майбутню історію умов праці за датами дії.

## Реалізовано

- Працівник — окремий об'єкт від користувача; необов'язковий зв'язок дозволений
  лише з активним користувачем відповідної компанії.
- Номер працівника, коди посад/підрозділів і номери договорів унікальні в компанії.
- Усі кадрові записи захищені компанійним доступом `employees.read/manage`.
- Права додаються міграцією та штатними RBAC seed-скриптами. Вони призначаються
  `admin` і новій ролі `hr_manager`. Інші ролі та призначення користувачів не
  отримують кадрового доступу автоматично.
- Додано необов'язковий `payment_iban`. Пробіли прибираються, літери переводяться
  у верхній регістр. Перевіряються формат українського IBAN та контрольна сума;
  `null` очищає реквізит. Це не перевірка власника/існування банківського рахунку.
  Джерело формату: [НБУ — IBAN](https://bank.gov.ua/ua/iban),
  [пояснення НБУ](https://bank.gov.ua/admin_uploads/article/Q%26A_IBAN.pdf).
- Батьківські підрозділи належать тій самій компанії; перевіряється весь ланцюг
  підпорядкування. Заборонені прямі та багаторівневі цикли.
- Підрозділ із активними дочірніми підрозділами/договорами та посаду з активними
  договорами не можна деактивувати. Активна дочірня структура потребує активного
  батьківського підрозділу.
- Нові/змінені договори не можуть посилатися на чужі або неактивні довідники.
- Дати договору узгоджені з прийняттям/звільненням працівника. Активний договір
  потребує активного працівника. Перед деактивацією працівника треба завершити
  його активні договори.
- Компанійне блокування серіалізує кадрові записи: одночасні зміни не обходять
  перевірку циклів, унікальності та перетину договорів.
- API відкочує всю операцію й журнал змін при помилці; сервіси не роблять commit.

## Договори — поточний контракт API

Збережена авторська модель: `contract_type`, необов'язкові `department_id` та
`position_id`, `work_arrangement`, `start_date/end_date`, статус
`active/ended/cancelled`. Активний договір має відкриту кінцеву дату; завершений —
явну кінцеву дату. Межі періоду включні: завершення 31 січня дозволяє наступний
договір із 1 лютого. Скасовані договори не беруть участі у перевірці перетину.

В основі 13.2 перетин будь-яких нескасованих договорів одного працівника в компанії
заборонений. Правила паралельних трудових відносин/сумісництва треба розширити в
13.3; поточна заборона не видається за повну реалізацію цих сценаріїв.

## Історія

Створення й фактична зміна працівника, підрозділу, посади або договору додають
`hr_changes`: стан до/після, компанія, об'єкт, автор та час запису. Повторне
збереження без змін не створює зайвого запису. Історія й поточний об'єкт
зберігаються в одній транзакції. API редагування/видалення історії відсутній.

Маршрути з префіксом `/api/v1/companies/{company_id}`:

- `GET /employees/{employee_id}/history`
- `GET /departments/{department_id}/history`
- `GET /positions/{position_id}/history`
- `GET /employment-contracts/{contract_id}/history`

Потрібне `employees.read`, зокрема для історії персональних/платіжних реквізитів.
API завжди фіксує автентифікованого автора. Для міграційного початкового знімка
чи прямого системного виклику без автора `changed_by=null`, без вигаданого автора.

## Міграції

Авторські `d9dbfdb5fb99` та `1bace2452a82`, уже застосовані локально, збережені.
Нова `13c2a7e9b001` виправляє серверний default статусу на `active`, додає
обмеження допустимих значень, IBAN та історію, реєструє кадрові права.
Існуючі кадрові записи отримують початковий знімок без зміни своїх сум/реквізитів.
Наявні невідповідні статуси не переводяться мовчки в інший стан: constraint
зупинить міграцію для перевірки даних.

Downgrade відмовляє за наявності історії або IBAN, щоб не втратити дані.
Створені ролі/права не видаляються при downgrade: вони можуть уже використовуватися.
Попередня авторська repair-міграція додає обов'язковий тип без заповнення та
видаляє два старі поля; її не слід використовувати для перенесення заповнених
старих договорів без окремого плану міграції. У перевіреній локальній базі всі
чотири кадрові таблиці до завершення 13.2 порожні.
