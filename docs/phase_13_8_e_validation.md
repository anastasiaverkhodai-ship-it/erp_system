# Phase 13.8-E — ізольована перевірка та безпечна зупинка

## Вихідний стан

- Git baseline: `583b0c856ac4abc720ed3d0d010648444f6624b2`.
- Очікувана ревізія основної БД: `13d4a7b8c025`. Міграції основної БД не запускалися.
- На початку Alembic показував єдиний head `13d4a7b8c026`.
  Файл `026` був untracked; файла `027` не було, і пошук його історії
  через `git log --all` нічого не знайшов. Немає локального доказу, що
  `027` існувала або була застосована. Очікуваний номер не є доказом міграції.
- Наявні незакомічені зміни та вісім резервних файлів збережено.

## Реалізовано

Нова міграція `13d4a7b8c027_payroll_insert_freeze.py` продовжує `026`.
Вона блокує INSERT salary slice для input, що вже використовується
розрахунком. INSERT/UPDATE/DELETE slices та початок розрахунку
серіалізуються через той самий рядок input. Лічильник змін рядка змушує
застарілі REPEATABLE READ / SERIALIZABLE транзакції завершуватися помилкою
серіалізації, а не використовувати старий набір джерел.

Початковий розрахунок бере блокування компанії, потім input, до читання
джерел. Виправлено попереднє перенесення декоратора блокування з публічної
функції на допоміжну функцію derivation. Commit/rollback залишаються
відповідальністю виклику.

Рядки нового розрахунку можна додавати лише в транзакції його створення.
`xid8` задається тригером, а не довіряється значенню клієнта. Після commit
рядки запечатані. Старі розрахунки отримують NULL creation transaction,
тому вже запечатані. UPDATE/DELETE продовжує блокувати міграція `026`.
Це запечатування на межі транзакції: первинні рядки в ній дозволені.
Воно не є доказом історичної достовірності джерел.

Скрипт ізольованої регресії додатково повідомляє ревізію джерела та
перевіряє її незмінність після тестів через READ ONLY транзакцію.
Ця перевірка не є повним порівнянням усіх даних основної БД.

## Межа доказу та незавершені gates

**C4-C заблоковано.** Встановлення тригерів сьогодні не доводить, що
джерела не змінювалися до встановлення. Наявні salary/additional-source
proof та minimum-wage rederivation звіряють поточні значення. Вони прямо
не засвідчують повну історичну незмінність. Збережений fingerprint,
обчислений із поточних рядків, не відновлює відсутній доказ минулого.

Крім того, `026`/`027` не закривають усі шляхи provenance: backdated
додаткові джерела, зміни нормативного контексту, періоду/контракту та
конкурентні зміни інших типів джерел потребують окремого повного протоколу.
Немає підстав прирівнювати freeze INSERT двох таблиць до такого протоколу.

Для історичних записів потрібні незалежно перевірені незмінні джерела,
пов'язані з моментом первинного розрахунку. Для майбутніх — атомарне
збереження повного versioned evidence та захист усіх його залежностей.
Автоматично позначати legacy рядки перевіреними заборонено.

**E3-C positive revision 2 заблоковано залежністю від C4-C.** Перевірка
`source_evidence_complete` не обходилася. Негативний E2E підтверджує
відмову без створення revision 2 / correction link. Фінансового виконання
не увімкнено. Фаза загалом не готова до commit або push як завершена.

## Відтворення

Усі PostgreSQL-тести виконувати тільки так:

```sh
PYTHONPATH=. .venv/bin/python scripts/run_postgresql_regression_copy.py tests/hr/test_payroll_insert_freeze_postgresql.py tests/hr/test_payroll_insert_freeze_contract.py
PYTHONPATH=. .venv/bin/python scripts/run_postgresql_regression_copy.py tests
```

Новий PostgreSQL-модуль перевіряє ім'я ізольованої БД та запускає справжній
Alembic CLI: upgrade `025 → 027`, downgrade `027 → 026 → 025`, повторний
upgrade. Решта історичних тестів зберігає власні контракти попередніх
ревізій. Повний suite на копії `025` не означає, що всі його тести виконані
на схемі `027`: новий модуль окремо встановлює та знімає цю схему.

Результати запусків та остаточний статус наведені нижче.

upgrade/downgrade, початкове створення двох рядків розрахунку, відкат,

після відмови перевіряється збереження slice та двох початкових рядків.

Ревізія основної БД залишилася `025`, копію видалено.
Лічильники цих запусків перекриваються; їх не слід додавати як унікальні тести.

## Продовження: знімок для коригування мінімальної гарантії (028)

Попередні результати вище описують стан до цього доповнення.

### Завершуваний обсяг

Поточний виконавець підтримує **лише зміну документованого контексту
мінімальної гарантії**: повної норми часу та класифікації наявного ручного
коригування. Він не є універсальним перерахунком зарплати, відпусток,
лікарняних або податків.

Під час нового первинного розрахунку зберігаються факти, використані для
мінімальної гарантії: версія правила, ставка, звичайний відпрацьований час,
норма, класифіковані суми до ручного коригування, саме коригування та
всі базові рядки нарахування. Знімок має версію, SHA-256 і прив'язку до
компанії, періоду, input та договору. Тригер 028 ставить позначку створення
лише під час INSERT розрахунку. Жоден старий розрахунок не оновлюється.

026 захищає заголовок/знімок від UPDATE/DELETE, 027 закриває пізнє додавання
рядків, 028 додатково блокує TRUNCATE заголовків. Відкат 028 із запечатаною
історією заборонено. Технічні колонки 027 залишаються під керуванням
тригерів, а не ORM; autogenerate явно виключає тільки ці три колонки.

Коригування повторює розрахунок мінімальної гарантії зі збережених фактів.
Воно **не перечитує сьогоднішні доплати, лікарняні, відпустки чи кадрові
умови** для заміни первинних сум. Відтворення первинної суми та кожного
рядка перевіряється до запису. Нова версія й посилання коригування
створюються в одному savepoint; зовнішній виклик керує commit/rollback.
Повтор однакового запиту повертає ту саму версію. Змінений fingerprint,
компанія, запит або неповний доказ призводять до відмови.

### Межа історичних доказів

Стара загальна C4-C-перевірка не стала доказом усієї історії. Замість
небезпечного підвищення її довіри реалізовано окремий доказ із явним scope
`minimum_wage_context_only`. Legacy записи без створеного одночасно з
розрахунком запечатаного знімка залишаються заблокованими. Довільний
перерахунок усіх залежностей та фінансові коригування вже проведених сум
не входять у цей виконавець. Активні проводки/виплати потрібно скасувати
або сторнувати через наявний процес перед створенням нової версії.

### API

Обидва методи вимагають `employees.manage` для компанії:

- `POST /companies/{company_id}/payroll-calculations/{id}/correction-evidence`
  — `request_key`, `reason`; повертає scope, повноту доказу й fingerprint.
- `POST /companies/{company_id}/payroll-calculations/{id}/minimum-wage-correction`
  — ті самі поля, `expected_source_fingerprint_sha256` і
  `corrected_minimum_wage_context`; повертає новий розрахунок.

Очікувані бізнес-відмови повертаються як HTTP 409, відсутній запис у
перевірці доказів — 404. Вхідний API не приймає знімок або прапорець довіри
від клієнта. Податкові результати, проводки та виплати автоматично не створюються.
